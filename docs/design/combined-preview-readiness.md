## Concrete exclusive handoff

Reserve **eight minutes** for six production-input cases on each of Qt 6.11.2 and
6.12.0, then **two additional minutes with Mike** for physical raw-pointer cases.
`./scripts/test_capture_broker_native.ps1` prints its plan without launching

The case runner creates at most three fixture hosts, or one separate test-owned
Win32 owner/popup, plus one passive selection overlay per attached display.
Each case has a separate process and a 40-second outer failure bound. Stop at
the first failure, a locked/unknown session, unexpected foreground, or a guarded
input-driver refusal. No bypass, virtual driver, global hotkey registration or
persistent setting change is part of this plan.

Receipts record Git head/dirty state, Python, Qt and QPA. Entry posts WM_HOTKEY
to the fixture with fake registration; real global shortcut chords and held
activation modifiers remain separate native gates.

The script and test harness generate no OS input. A separately authorized guarded
driver follows `driver-request.json`, restricted to its declared owned handles:
Escape down/up or a left-button drag through the small physical fixture rectangle.
Fixture-injected pointer interpretation is explicitly separate from the default
production route. Only the additional human lane can qualify physical raw input;
real callback counters and actual capture completion are required. Installation
or an instruction file alone never establishes success. The portable QPA guard
contracts use a forbidden worker factory under both simulated platform names,
so selecting Windows QPA for a broad test run cannot turn those unit controls
into real input acquisition. A dropped-guard source fault is rejected before
any native worker can be constructed.

Capture observations use a RAM-only canonical sink: **no captured image is
written to disk, the clipboard, or an editor**, including unexpected full-frame
or Escape images. This lane qualifies input, selection and preservation only;
it does not qualify production delivery. Receipts contain ownership, geometry,
counts and errors, with no screenshots. Exact region geometry and cardinality
remain assertions. Preservation checks include existing handles, visibility,
modality, popup/grabs, focus/action identities, and for the external peer a reply
correlated to a post-terminal request. The foreign popup observer uses documented
[GUITHREADINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-guithreadinfo)
and [TrackPopupMenuEx](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-trackpopupmenuex).
Transient focus events remain diagnostic traces; identity observations do not
prove every intermediate focus state.

Cleanup first cancels only the owned capture and independently confirms every
native worker stopped and cleaned. Only then may fixture dialogs/menus close.
Failure to confirm cleanup fails the case and uses only its owned process-tree
abort; it is never a successful preservation result. The external peer has its
own 45-second watchdog. No normal application window is a teardown target.

## Portable gaps closed in this checkpoint

The three concrete candidates from mutation assessment were:

1. Cleanup callbacks in the final second of the two-second watchdog. A controlled
   half-second remainder now checks rearming, retained busy/scope ownership, the
   actual deadline receipt, and cleanup only after process exit.
2. A queued operation timeout after its reply. The idle warm helper must remain
   alive and accept the next request. Dropping the pending-request guard kills
   that helper; the new assertion rejects this fault.
3. Positive diagnostic times. Nonzero clock origins now check relative
   milliseconds, and a deliberately late operation callback checks 125 ms of
   lateness. Zero-only clocks could not detect wrong units or origin arithmetic.

These are four tests. Independent source-level replay rejected six faults:
early cleanup threshold, missing idle guard, null elapsed time, wrong elapsed
units, added rather than subtracted origin, and wrong lateness sign. This is
fresh semantic evidence, not a revised aggregate mutation score. Four further
portable cases check the exact Windows helper argument vector and independent
missing-host/missing-script refusal, plus the absolute fallback host when
`SYSTEMROOT` is absent, without executing a helper. The fallback assertion uses
Windows path semantics and case-insensitive comparison. No production
behavior changed for these tests.

The full randomized Qt 6.12 suite also exposed test-process logging leakage:
entry-point tests replaced root handlers with a stream tied to temporary pytest
stderr, then later tests logged through the closed stream. Their fixture now
detaches and restores prior handlers/level and closes only its own handlers.
This fixes test isolation without suppressing logging errors or changing the
application's production logging setup. Preserve the triggering run alongside
the corrected same-order run.

That clean-logging run exposed a separate premature observer timeout in the
cleanup-callback integration test: pytest-qt stopped at its default five seconds,
before the unchanged eight-second startup policy expired. The observer now uses
the existing protocol-test budget of startup + operation + one-second reporting
margin; production deadlines and completion/cleanup assertions are unchanged.
Another randomized run exposed the same five-second mismatch in the bad-startup
handshake case. Protocol reply observers now consistently derive their bound
from the configured startup + operation budgets + one-second reporting margin;
the chained two-reply case accounts for both operations. Cleanup, idle and owner
destruction observers and all protocol/phase assertions retain their contracts.
The delayed child startup's exact cause is unproven. This repairs the tests'
budget mismatch, not evidence of a diagnosed native helper stall.
