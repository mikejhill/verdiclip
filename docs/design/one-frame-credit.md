# One-frame credit protocol: design candidate

Status: isolated portable implementation candidate; independent code and native qualification pending. The successful retained-frame candidate and workflow remain unchanged. This stage does not enable UI capture, multiframe capture or a release.

## Purpose and explicit version

Introduce a protocol-level wait for authorization to send one bounded body chunk. This is not a claim that Windows WriteFile or ReadFile is blocked. The first stage remains one observed frame, at most 1024 by 512 tightly packed RGB24 pixels, with the existing 128-byte header, canonical observation, digest checks and actual binary EOF.

Use control envelope VERSION=2, PEER_SCHEMA=3 and CREDIT_SCHEMA=1. PeerLaunch is the launch schema: its existing peer_schema becomes3 and its exact field set gains credit_schema=1; there is no separate unnamed launch revision. Ready must contain protocol_version=2, peer_schema=3 and credit_schema=1, which the parent verifies before ready is public. Put the pure fixed credit codec/state primitive at verdiclip.capture.frame_credit; the fixed RuntimeManifest/bootstrap schema becomes4 and its attested origin tuple gains this exact module. The fixed installed verifier checks its actual loaded origin and wheel bytes. No arbitrary module dispatch is added. No auto-negotiation, mixed-version acceptance or fallback to the successful uncredited protocol. Update exact installed-module attestation and independent wheel-byte checks for all new primitives. Retain previous candidate evidence as evidence of its own version.

Add two fixed envelope kinds, frame_wait (peer to parent) and frame_credit (parent to peer). The outer request_id is the existing observe request ID. The exact payload contains credit_schema=1, epoch, frame_id=1, chunk_index, offset and count. Epoch is the existing fixed 32-hex session epoch. All numeric fields require exact integers, not booleans/floats. Unknown or duplicate keys, fields, messages, versions, directions or phases fail permanently.

N is the already validated image length. C=65536. K=ceil(N/C), at most24. Chunk indices are0..K-1; offset=index*C; count=min(C,N-offset). Neither endpoint chooses arbitrary slices. Credit consumes a transfer sequence, not a new command request ID; the existing128 command request cap is unchanged. Header bytes are not charged as body credit and are limited to exactly128 before any first grant.

## Peer state and wait witness

After successful observation, send the existing canonical metadata response and128-byte header. Set WAITING_CREDIT(i) before sending frame_wait(i). The peer may not send any body byte for i until it reads and validates the exact matching frame_credit(i) under the original observation deadline. The conforming parent never queues a credit before the corresponding announced wait. The synchronous peer reader validates its protocol state and exact next token, but cannot determine whether a matching future credit was already buffered in the kernel before its announcement. Thus no credit-in-advance claim is made about a malicious transport producer or kernel arrival timing. It never intentionally buffers a future credit itself. A duplicate, wrong sequence, wrong identity, wrong count, unexpected finish or malformed control message is terminal failure.

A matching credit is consumed once before the write. Write exactly count bytes in existing bounded native calls, with existing parent-liveness and deadline checks. Then either announce WAITING_CREDIT(i+1), or, after the final chunk, close the binary pipe and follow the existing control finish/EOF/natural-cleanup protocol. No frame success is inferred from a wait or final chunk count.

The wait witness is narrow: the peer has declared its state as awaiting authorization and the parent has issued no matching credit. Receipt of the announcement does not prove the peer has entered a blocking ReadFile call, is currently scheduled, or is blocked by OS backpressure. The forbidden next body write is the stable protocol fact.

## Parent state and public facade

The worker remains single-flight until the complete frame, actual EOF and existing terminal lifecycle gates finish. Before initial credit it requires the paired canonical observation/header, native peer identity and valid frame length. For each chunk it maintains one pending wait, zero-or-one consumed grant, cumulative granted bytes and cumulative accepted bytes. Accepted bytes cannot exceed granted bytes; each chunk must be fully accepted into the existing sink before another grant is sent. A next wait may arrive on the control pipe while the previous binary bytes are still being drained: retain at most that one exact next wait, but do not expose it as grantable until the previous chunk is fully accepted. Any further wait is failure.

Proposed narrow public API:
- credit_required(generation, metadata_bytes): metadata only, exact request/frame/epoch/index/offset/count, emitted once when the worker has a grantable wait.
- grant_frame_credit(generation, request_id, chunk_index): owning-thread method. It validates the current immutable pending token and queues one bounded grant to the worker. The worker revalidates generation, phase, token, cancellation and deadline immediately before the pipe write. No user-supplied byte count, payload, path or arbitrary operation.

Facade token consumption is synchronous on its owning thread BEFORE queue emission: validate exact generation/request/chunk against its current immutable pending token, remove that token, then emit exactly one metadata-only grant. A second call cannot queue a second grant. Invalid or duplicate grant calls latch cancellation/invalidate the frame before raising; they do not leave the transfer running. The worker independently revalidates the token, so stale queued grants cannot authorize anything. credit_required forwarding filters generation, current busy-observe phase and cancellation/closing/terminal state; duplicate or inconsistent same-generation tokens fail rather than overwrite a pending token. A stale-generation event is ignored and cannot revive any grant. Restart remains prohibited by the current facade.

This is a public bounded consumer-capacity gate: a caller grants only when it can accept the next bounded chunk into its reserved sink. It is not a fixture-only debug flag or arbitrary pause hook. There is no automatic grant in this first proof. The harness grants each announced chunk for the success case. Holding the first or an interior grant is a real bounded flow-control choice, not a hidden debug latch. It will also permit a future bounded consumer coordinator to control capacity, but no multiframe/credit replenishment window is implemented in this stage. If GUI scheduling makes24 round trips too slow, preserve that failure; do not enlarge the original operation budget.

A public cancel after credit_required with no grant issued for that token is the cancellation experiment. Record the immutable announced token, cumulative accepted/granted counts and absence of a grant before cancel. Cancellation atomically latches before any queued grant can execute. An already queued grant is not this strong phase witness and must be labeled separately. The cancellation receipt must additionally contain a worker-authored immutable credit witness, not just GUI observations: exact pending token, peer-wait receipt sequence/time, cumulative granted and accepted bytes, last committed grant sequence, cancellation-latch sequence/time and worker-observed cancellation sequence/time. Capture the pending state at cancellation and a final state after transport cleanup; neither may show a grant reservation or committed grant for the held token. Use one small shared synchronization boundary for cancel latching and grant reservation. Do not hold it across pipe I/O, copying or hashing. A reservation committed before cancellation counts as an issued grant even if its write later fails; that outcome cannot qualify the no-grant wait experiment. Once cancel wins that boundary, no queued grant may reserve or commit. Worker cancellation handling snapshots its counters, stops credits and preserves the original failure through cleanup. Record bounded ordered event metadata (at most24 grants/waits), not pixel buffers. Tests must force each ordering and reject a forged or incomplete witness. The first-wait case requires accepted=granted=0. The interior case requires at least one complete accepted chunk and accepted=granted=held-token.offset; no partly outstanding earlier credit may qualify.

The independent harness validates both the public event and this worker-side terminal witness, including no grant for the held token before AND after cancellation. The public event alone is insufficient. No raw pixel data crosses a queued signal.

## Bounded queues and memory

Retain the existing16KiB maximum control envelope and64KiB binary read buffer/turn cap. Each complete encoded frame_wait/frame_credit control record has a strict512-byte budget INCLUDING the4-byte length prefix, entire JSON envelope and payload. Thus its length-prefix value must be at most508; ordinary control records retain their existing16KiB maximum. The strict per-kind cap is checked before encoding/admission, and the bounded decoder rejects a credit-kind record exceeding it. The parent can hold one grantable/next wait and at most one queued credit command; facade duplicate grants fail instead of accumulating queued work. The peer reads one credit synchronously and never buffers future grants. Control transport still needs an explicit bounded read buffer and parser limit: reject more than the maximum legal transcript, not merely individual large messages. For this one-frame phase allow at most K waits and K credits, one observation response, existing ready/finish messages, and no surplus credit events. A fixed64-message transfer cap is sufficient and does not enlarge the normal128-request cap.

The retained sink remains N mutable and at most N frozen bytes; credit does not remove the freeze overlap. Continue the documented channel-local 2N+3C+128 receive-side accounting and separate native/kernel/provider/metadata allocations. Grant only after existing storage is available. Credit is not a global memory lease and does not account for consumer-owned aliases after take.

Raw pipe segmentation is not a chunk boundary: fragmented native writes/reads are allowed, but exact cumulative byte allowance is enforced. Cross-pipe delivery order cannot prove when bytes entered the kernel relative to a grant; the claim concerns the trusted peer state machine and parent admission, not a forensic kernel-arrival timestamp. Final digest, identity and EOF remain mandatory.

## Failure, cancellation, EOF and disposal

Failure/cancel is irreversible. Stop future grants, close both pipes, run existing OwnedHelper termination/cleanup, invalidate the vault, and discard mutable/frozen candidates under existing ownership rules. The GUI never clears mutable pixels or hashes them. No resume, credit refund, retry, method switch or partial result is available. A duplicate/stale grant cannot authorize a reused request or frame.

Premature EOF, excess/trailing bytes, missing chunk bytes, incomplete control envelope, surplus wait/credit, wrong correlation and timeout fail. Complete N bytes without actual binary EOF is not success. Hash validation/freeze still completes within the original observe deadline; sealing/publication still requires existing natural cleanup, terminal/Qt-finished evidence and current vault authorization. Credit does not alter the known Qt-finished-versus-native-join limitation.

Cancellation at a no-credit wait proves controlled protocol cancellation and disposal, not OS blocked-write cancellation. Parent death is a separate test: pin exact parent/peer process identities beforehand, kill only the parent, prove peer death/natural job retirement with the existing independently held handles. No cancellation receipt can substitute for parent-death evidence, and fallback cleanup cannot upgrade either outcome.

## Deadlines and qualification

Every wait, credit validation, pipe write, read, digest and freeze uses the SAME original2s observation deadline; nothing restarts it. Existing worker-entry3s startup/20s session stamps and retiring5s allowance are unchanged, including current retirement semantics. Existing outer fixture preparation10s, capture15s and absolute25s caps remain. A withheld credit expires normally unless public cancellation arrives earlier. No grace period or polling reset.

Portable gates: both strict codecs and state machines; every partial chunk split; credit before wait, duplicate/third queued events, wrong epoch/request/frame/index/count, reversed direction, stale generation, exact deadline boundaries before/after blocking calls; no next grant until exact previous acceptance; pending next wait arriving before binary drain; surplus/trailing EOF; malformed credit; cancellation before/after queued grant; sink/vault disposal and terminal ordering.

Fresh installed-wheel native first gate remains success only: actual default channel/fixed attested peer, exact source/runtime origins, full independent reference, direct immutable retained-byte comparison and single take, all previous state/ownership/retirement checks. Then separate explicit cases hold the first grant and one interior grant and call public cancel only after the corresponding public wait witness. They must show no admitted image, no later credit, bounded cleanup and exact retained process evidence. A deadline-withheld-credit case remains failure, never successful capture. No artificial sleep to assert a phase. Separate parent-death case requires its own process witnesses. No multiframe, app UI, general-app, responsiveness, OS blocked-write or release qualification follows automatically.

## Current implementation boundary

The public `credit_required` signal carries one length-prefixed `frame_wait` record as immutable bytes. `grant_frame_credit(generation, request_id, chunk_index)` consumes that pending public token before queueing a matching `frame_credit`. The transfer state lives in the worker; `CreditGate` is the short shared cancellation/reservation lock. Header/metadata pairing and reserved sink allocation precede any public grant.

Terminal credit snapshots encode event history as bounded arrays `[sequence, monotonic_ns, kind, chunk_index_or_null]` instead of repeating full token dictionaries. The full pending token remains in each snapshot. This keeps maximum late-cancellation evidence under the existing metadata budget. The original observation, terminal and frame identities remain independently bound by the retained sink.

The successful uncredited installed-wheel receipts remain valid only for that earlier candidate. The current isolated success-harness candidate explicitly grants each public token and retains an independent bounded transcript. It checks all public wait/grant calls against the worker's exact wait/reservation event order, total bytes and original observation deadline before taking the retained image. Full-reference comparison and natural ownership cleanup remain required. This adaptation requires separate review and a fresh installed-wheel native proof. First/interior cancellation and parent-death experiments require separate reviewed harness evidence; portable tests alone do not qualify those native cases.
